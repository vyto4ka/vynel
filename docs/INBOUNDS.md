# Инбаунды и IP-адреса

> **Статус:** модель «профиль → инбаунд ноды», правила доступа групп, привязка к IP (`listen`/`sendThrough`), раскладка портов и все роли на одном IP реализованы. Не реализованы: `vynel net add-ip` (§2.6), выбор IP в установщике (§2.7), теги нод в правилах доступа.

Две задачи:

1. **Много нод с почти одинаковым конфигом, но у каждой свой VLESS-профиль.** Свой тег (`VLESS_NL`, `VLESS_DE`), свои ключи, свой SNI. Доступ можно выдавать как по отдельной ноде, так и «ко всем сразу».
2. **Несколько IP на одном сервере.** Например, на основном сервере три адреса: панель, подписки и VLESS, каждый на своём IP.

Документ уточняет модель из [ARCHITECTURE.md](ARCHITECTURE.md) и [PROFILES.md](PROFILES.md). Там, где они расходятся, правильно то, что написано здесь.

## 1. Модель: профиль → инбаунд ноды

### 1.1 Было (ревизия 3)

Один профиль с одним общим тегом `vless-reality` на всех нодах. Простая схема, но у неё два минуса:
- нельзя дать группе доступ к NL, но не к DE — инбаунд один на всех;
- в статистике Xray по инбаундам и в логах все ноды выглядят одинаково.

### 1.2 Стало

Три уровня, как наследование классов:

```
Шаблон (в коде)          A: Reality self-steal      B: XHTTP VK CDN
      │ создаётся админом один раз
      ▼
Профиль (общий конфиг)   «Reality 443»               «VK CDN»
  настройки по умолчанию: порт, sockopt, sniffing, fingerprint, extra, ...
      │ применяется к ноде → автоматически создаётся
      ▼
Инбаунд ноды             VLESS_NL   VLESS_DE   VLESS_FI   CDN_NL
(= «свой VLESS-профиль»)  свой тег, свои ключи Reality и shortId, свой домен/SNI,
                          свой IP, свои override поверх профиля
```

| Уровень | Что хранит | Кто меняет |
|---------|-----------|------------|
| **Шаблон** | Структура инбаунда, переменные, Caddy, проверки, lint (PROFILES.md) | Разработчик |
| **Профиль** | Значения по умолчанию для всех своих инбаундов: порт, sockopt, sniffing, fingerprint, `extra`, шаблон тега, шаблон названия | Админ, один раз |
| **Инбаунд ноды** | Тег, переменные ноды (домен, ключи, shortId), IP привязки, локальные override | Создаётся сам при добавлении профиля на ноду, правится по необходимости |

Соответствие Remnawave:

| Remnawave | У нас |
|-----------|-------|
| Config Profile `NL` с инбаундом `VLESS_NL` (JSON копируется и правится руками под каждую ноду) | **Инбаунд ноды** `VLESS_NL`, создаётся автоматически из профиля |
| — (нет общего уровня) | **Профиль**: общие настройки, меняются в одном месте для всех нод |

### 1.3 Тег инбаунда

- Шаблон тега задаётся в профиле, по умолчанию `VLESS_${NODE_CODE}` для A и `CDN_${NODE_CODE}` для B.
- `NODE_CODE` — короткий код ноды. По умолчанию он берётся из страны (`NL`). Если такой уже есть, добавляется номер (`NL2`). Код можно поменять.
- Если на ноде несколько инбаундов одного профиля (например, на разных IP, §2), добавляется суффикс: `VLESS_NL_2`.
- Тег глобально уникален. Он служит ключом для статистики по инбаундам, для логов и для UI.
- Тег можно переименовать. В Xray он сменится при следующем применении, а связи с группами и точками подключения хранятся по `id`, поэтому ничего не ломается.

### 1.4 Наследование и override

Итоговый JSON инбаунда собирается так:

```
render(шаблон, переменные профиля + переменные инбаунда ноды)   ← база
  ⊕ override профиля        (JSON merge patch)
  ⊕ override инбаунда ноды  (JSON merge patch)
  ⊕ системные поля          (clients, listen=IP привязки, tag)
```

В UI инбаунда ноды каждое поле помечено:
- **«из профиля»** (серым) — изменится, если поменять профиль;
- **«изменено на ноде»** (подсвечено) — с кнопкой «вернуть как в профиле».

При сохранении профиля показывается превью: «изменение затронет 12 инбаундов на 12 нодах; у 2 из них это поле переопределено локально — они не изменятся» и кнопка «применить и к ним тоже».

Так выполняется цель «конфиг ± одинаковый»: всё общее живёт в профиле, а каждая нода хранит только свои отличия (домен, ключи, IP, редкие исключения).

### 1.5 Доступ групп

Раньше группа ссылалась на инбаунды профиля. Теперь в группе хранится **список правил доступа**:

| Тип правила | Пример | Что даёт |
|-------------|--------|----------|
| Инбаунд ноды | `VLESS_NL` | Ровно этот вход |
| Профиль целиком | «Reality 443 — все ноды» | Все инбаунды этого профиля, **в том числе на нодах, добавленных позже** |
| Нода целиком | «Нидерланды — всё» | Все инбаунды ноды (Reality и CDN) |
| Тег ноды | `eu`, `premium` | Все инбаунды нод с этим тегом (позже, не в MVP) |

Эффективный доступ пользователя = объединение правил всех его групп, развёрнутое в набор инбаундов нод. Это множество пересчитывается при изменении групп, нод или профилей и кэшируется для reconciler и подписок.

Пример:
- «Основная» = профиль «Reality 443» целиком → новые ноды подключаются к ней сами;
- «Мобильные» = профиль «VK CDN» целиком;
- «Тест DE» = только `VLESS_DE`.

### 1.6 Точки подключения

Одна точка подключения на каждый инбаунд ноды, создаётся автоматически (как в ARCHITECTURE.md §6.3). Адрес по умолчанию — **домен, привязанный к IP этого инбаунда** (§2). Можно добавить дополнительные точки к тому же инбаунду, например второй адрес или CDN.

## 2. Несколько IP-адресов на сервере

### 2.1 Цель

На основном сервере (панель + нода) три IP:

```
IP1  203.0.113.10   panel.example.com   → панель (UI/API) + gRPC для нод
IP2  203.0.113.11   sub.example.com     → подписки
IP3  203.0.113.12   nl.example.com      → VLESS Reality (VLESS_NL)
```

Зачем:
- **Блокировка VLESS-IP не задевает панель и подписки.** Если РКН забанит IP3, панель и подписки продолжат работать. Заказываешь новый IP, меняешь его в ноде, клиенты обновляют подписку — и всё.
- **IP панели нигде не светится.** Его нет ни в подписках, ни в конфигах клиентов. Подписки на отдельном IP тоже не выдают панель.
- **Не нужна схема «Reality перед панелью».** У каждого сервиса свой `:443`, конфиг Caddy и Xray проще.
- **Один сервер вместо трёх**, если хостер даёт дополнительные IP.

**Роли можно совмещать как угодно**, в том числе панель и подписки на одном IP:

```
IP1  203.0.113.10   app.example.com     → панель (:47321, секретный путь) + gRPC для нод
                    static.example.com  → подписки (:443)
IP2  203.0.113.12   nl.example.com      → VLESS Reality (VLESS_NL)
```

Если панель и подписки на одном `IP:порт`, Caddy разводит их по SNI. Если порты разные, они вообще не пересекаются (STEALTH.md §2.1). Домены у панели и подписок остаются разными.

Это работает на любой ноде, не только на основной. Например, на NL два IP → два Reality-инбаунда `VLESS_NL` и `VLESS_NL_2` (резерв или разные группы).

### 2.2 Модель

```
node_addresses   id, node_id, ip, family(v4|v6), interface,
                 on_interface(bool),   -- агент видит адрес на интерфейсе
                 is_primary(bool),     -- адрес маршрута по умолчанию (src)
                 label, note
domains          id, name, address_id, purpose(panel|sub|inbound|cdn_origin),
                 dns_ok(bool), dns_checked_at
```

**Роли адреса.** Это не отдельная сущность — роли вычисляются из того, что к адресу привязано:

| Роль | Что привязано | Где задаётся |
|------|--------------|--------------|
| Панель | `panel_address_id` в настройках | Только на локальной ноде (сервер панели) |
| Подписки | `sub_address_id` в настройках | Только на локальной ноде |
| Шлюз нод (gRPC `:9443`) | по умолчанию IP панели | Настройки |
| Вход инбаунда | `node_inbounds.listen_address_id` | Инбаунд ноды |
| Выход инбаунда | `node_inbounds.egress_address_id` (по умолчанию = вход) | Инбаунд ноды |

Агент при каждом подключении присылает список адресов на интерфейсах (`ip -o addr show scope global`). Панель синхронизирует `node_addresses` и предупреждает, если к адресу что-то привязано, а на интерфейсе его больше нет.

### 2.3 Раскладка портов: универсальный резолвер

Вместо фиксированных схем рендерер собирает таблицу «кто что хочет слушать» и раскладывает её автоматически:

```
вход:  список потребителей (сервис, IP, порт, протокол, домены)
       - panel      IP1:443  tls  [panel.example.com]
       - sub        IP2:443  tls  [sub.example.com]
       - VLESS_NL   IP3:443  reality, self-steal домен nl.example.com
       - CDN_NL     IP3:443  через Caddy, origin домен origin.example.com
       - gateway    IP1:9443 grpc mTLS

правила:
  1. (IP, порт) с единственным потребителем → он слушает напрямую
  2. (IP, 443) с Reality + TLS-сайтами Caddy → Xray Reality на IP:443,
     target = Caddy 127.0.0.1:<локальный порт для этого IP>, Caddy разводит по SNI
  3. (IP, 443) с несколькими TLS-сайтами Caddy → Caddy на IP:443, разводка по SNI
  4. два Reality на одном (IP, порт) → ошибка конфигурации
  5. :80 на каждом IP, где есть домены с ACME → Caddy (HTTP-01 + редирект)
```

Итог для примера из §2.1:

```
IP1:80    Caddy  ACME + редирект       panel.example.com
IP1:443   Caddy  → листенер UI/API
IP1:9443  vynel panel gRPC (mTLS)
IP2:80    Caddy  ACME + редирект       sub.example.com
IP2:443   Caddy  → листенер подписок
IP3:80    Caddy  ACME + редирект       nl.example.com, origin.example.com
IP3:443   Xray   Reality VLESS_NL      → чужой трафик → Caddy 127.0.0.1:8443
                                           ├─ nl.example.com     → сайт-заглушка
                                           └─ origin.example.com → XHTTP CDN_NL
```

Для сервера с одним IP тот же резолвер даёт старую схему (ARCHITECTURE.md §13): Reality на `:443`, за ним Caddy с панелью, подписками и заглушкой по SNI. Новый код для этого случая не нужен.

Конфликты (`IP:порт` занят чужим процессом, два Reality на одном адресе, домен, привязанный к IP, у которого нет A-записи) показываются **до** применения, в превью раскладки.

### 2.4 Привязка в конфигах

**Xray**: вход и выход по IP инбаунда.

```json
{ "tag": "VLESS_NL", "listen": "203.0.113.12", "port": 443, ... }

"outbounds": [
  { "tag": "DIRECT",          "protocol": "freedom", "settings": { "domainStrategy": "UseIPv4" } },
  { "tag": "DIRECT@203.0.113.12", "protocol": "freedom", "sendThrough": "203.0.113.12",
    "settings": { "domainStrategy": "UseIPv4" } },
  { "tag": "BLOCK", "protocol": "blackhole" }
]
"routing": { "rules": [
  ...блокировки из базового конфига...,
  { "type": "field", "inboundTag": ["VLESS_NL"], "outboundTag": "DIRECT@203.0.113.12" },
  { "type": "field", "network": "tcp,udp", "outboundTag": "DIRECT" }
]}
```

- Outbound `DIRECT@<ip>` и правило `inboundTag → outbound` добавляет рендерер. В базовом конфиге их нет. Они вставляются **после** правил блокировки, так что блокировки продолжают работать.
- Зачем `sendThrough`: без него трафик клиентов уходит в интернет с основного IP сервера, то есть с IP панели. Сайты видят IP панели, а жалобы на трафик приходят на него. Выход с IP3 полностью отделяет VLESS от панели.
- Выход можно поменять вручную, например «вход IP3, выход IP4».

**Caddy**: каждый сайт получает `bind` на свой IP.

```caddy
https://panel.example.com { bind 203.0.113.10  reverse_proxy 127.0.0.1:<ui> }
https://sub.example.com   { bind 203.0.113.11  reverse_proxy 127.0.0.1:<sub> }
http:// { bind 203.0.113.10 203.0.113.11 203.0.113.12  redir https://{host}{uri} }
https://nl.example.com:8443 { bind 127.0.0.1 ... }
```

**Панель**: листенеры UI, API, подписок и gRPC тоже слушают конкретные адреса (UI и подписки — только `127.0.0.1`, gRPC — на IP1). Даже если Caddy настроен неверно, на IP3 панели нет.

### 2.5 Исходящие соединения самой панели

ACME, Telegram, проверки CDN и самотесты идут с основного IP (`is_primary`, адрес маршрута по умолчанию). Рекомендация в мастере: **основной IP сервера = IP панели**. Тогда на IP VLESS не ходит ничего служебного.

Если основной IP занят под VLESS (у некоторых хостеров дополнительный IP нельзя сделать основным), служебный трафик панели можно привязать к IP1 через настройку «Исходящий IP панели» (`net.Dialer.LocalAddr`).

### 2.6 Дополнительные IP на интерфейсе

У одних хостеров дополнительный IP появляется на интерфейсе сам, у других его нужно прописать в netplan.

- Агент показывает адреса, которые видит. Если адрес, указанный в панели, не найден, нода пишет «IP 203.0.113.12 не настроен на сервере».
- Страница-инструкция ноды в этом случае показывает готовый фрагмент netplan под интерфейс и шлюз сервера.
- Команда `vynel net add-ip 203.0.113.12/32` применяет netplan **с автоматическим откатом**: если в течение 60 секунд не подтвердить `vynel net confirm`, конфиг откатывается. Так ошибка в сети не отрежет доступ к серверу. Аналог `netplan try`.

### 2.7 Установка с несколькими IP

```bash
bash <(curl -fsSL https://.../install.sh) panel \
     --panel-domain panel.example.com --panel-ip 203.0.113.10 \
     --sub-domain   sub.example.com   --sub-ip   203.0.113.11 \
     --with-node    --node-domain nl.example.com --node-ip 203.0.113.12
```

- Если флагов `--*-ip` нет, а на сервере найдено больше одного глобального IP и установщик запущен в терминале, он спрашивает интерактивно («какой IP под панель / подписки / VLESS»). Без терминала всё ставится на основной IP. Полный сценарий вопросов — INSTALL.md §2.
- Перед выпуском сертификатов установщик проверяет, что каждый домен резолвится в свой IP.
- Позже всё меняется в панели: «Сервер панели → Сеть». Смена показывает превью раскладки и предупреждает, что нужно поменять DNS-записи.

### 2.8 Замена заблокированного IP

Типовой сценарий, ради которого всё это делается:

1. Бот: «⚠ Самотест VLESS_NL не проходит» (или жалобы пользователей).
2. Заказываешь у хостера новый IP4 и добавляешь его на интерфейс (`vynel net add-ip`, §2.6).
3. В панели: инбаунд `VLESS_NL` → вход IP4. Панель показывает: «поменяйте A-запись `nl.example.com` → IP4» и проверяет DNS.
4. Применить → Xray слушает IP4, Caddy получает сертификат на новом IP.
5. Клиенты обновляют подписку. Если в точке подключения стоит домен, а не IP, после смены DNS они продолжат работать даже без обновления.

Панель и подписки всё это время работают.

## 4. Как это выглядит в мастере добавления сервера

ARCHITECTURE.md §6 остаётся с тремя шагами, но внутри они меняются:

1. **Нода.** Название, страна (из неё — код `NL`), домен. После установки агента появляется список IP сервера. Если IP несколько, у каждого выпадающий список «для чего».
2. **Профили.** Галочки «Reality 443», «VK CDN». Для каждой — какой IP (по умолчанию основной) и домен. Инбаунды `VLESS_NL` и `CDN_NL` создаются сразу, ключи генерируются. Внизу превью раскладки портов (§2.3).
3. **Точки подключения и доступ.** Точки созданы. Здесь же видно, в какие группы инбаунд попал автоматически (через правило «профиль целиком»), и можно добавить его в отдельные группы.
