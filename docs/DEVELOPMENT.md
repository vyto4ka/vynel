# Разработка

## Требования

- **Go 1.21+.** Нужная версия (1.26, её требует `xray-core`) скачается сама через `GOTOOLCHAIN=auto`.
- **Linux или WSL2.** Процессы Xray и nginx управляются через Linux-API.
- **Для интеграционных тестов:** nginx с модулем stream из пакетов (`sudo apt install nginx libnginx-mod-stream`). Xray, Pebble (тестовый сервер ACME от Let's Encrypt) и Caddy (для агентов старых панелей) `make test-integration` сам скачает и соберёт в `.cache/`.
- **Генераторы protobuf** — только если меняешь `.proto`: `buf`, `protoc-gen-go`, `protoc-gen-go-grpc` (ставятся через `go install …`).

## Команды

```bash
make build              # bin/vynel
make build-all          # bin/vynel-linux-amd64, bin/vynel-linux-arm64
make test               # быстрые тесты (без Xray, nginx, Pebble часть тестов пропускается)
make test-integration   # всё, включая сквозные тесты на настоящих Xray, nginx и Pebble
make xray caddy pebble  # только скачать или собрать бинарники в .cache/
make lint               # golangci-lint
make proto              # перегенерировать internal/proto из proto/
make web                # собрать веб-интерфейс (web/dist, вшивается в бинарь; без него панель пишет «not built»)
```

```
  xray/                     процесс Xray, проверка конфига (xray -test), gRPC API Xray
  nginxconf/                генератор nginx.conf: сайты, SNI-роутер (stream), строгий SNI, проверка директив шаблонов;
                            метки @@...@@, которые агент заменяет своими путями
  certs/                    сертификаты: временный самоподписанный, Let's Encrypt по HTTP-01 (x/crypto/acme),
                            продление, локальный CA (issuer internal), перенос из Caddy
  caddyconf/                генератор JSON-конфига Caddy (для агентов старых версий)
  decoy/                    встроенные сайты-заглушки (cloud, studio, docs, coffee, journal)
  jointoken/                токен подключения ноды (vyn1.…)

  panel/
    store/                  SQLite: миграции (store/migrations), запросы
    service/                вся бизнес-логика: ноды, профили, группы, пользователи, статистика,
                            точки подключения, HWID, раскладка nginx (и Caddy для старых агентов), желаемое состояние нод
    reconciler/             рассылка желаемого состояния нодам (снапшот / дельта), обслуживание
    gateway/                gRPC-сервер для нод (Join + Connect по mTLS)
    subscription/           HTTP подписок: форматы, правила клиентов, страница, заглушки
    webapi/                 веб-панель: вход, JSON API (/api/…), раздача web/dist под секретным путём
    ca/                     внутренний CA
    app/                    сборка процесса панели
  node/
    agent/                  агент ноды: сессия с панелью, применение к Xray и nginx, сертификаты для Xray, статистика
    nginx/                  свой экземпляр nginx (дочерний процесс): nginx -t, SIGHUP, сертификаты, заглушки
    caddy/                  процесс Caddy для панелей старых версий
    firewall/               nftables: открыто только то, что обслуживает vynel; шлюз нод — только адресам нод
    state/                  bbolt: применённое состояние, очередь статистики
    metrics/, sysctl/       метрики хоста, BBR/fq/TFO
  e2e/                      сквозные тесты (панель + ноды + настоящие Xray и веб-сервер)
web/                        фронтенд: React + Vite + TypeScript (src/pages — разделы, src/ui.tsx — компоненты,
                            src/styles.css — тема); собирается в web/dist и вшивается через web/embed.go
proto/                      .proto
scripts/                    install.sh (установщик: aio, panel, node, update, uninstall), install-aio.sh (переходник
                            для старых ссылок), fetch-xray.sh
docs/                       документация
```

Главное правило: **транспорты не содержат логики.** CLI, веб, а позже бот вызывают методы `internal/panel/service`. Каждое изменение записывается в журнал (`audit_log`) и в очередь событий (`events_outbox`) в той же транзакции.

## Как это работает внутри

1. **Желаемое состояние.** Любое изменение запускает в reconciler пересчёт желаемого состояния каждой ноды (`service.DesiredStates`). Оно включает конфиг Xray без клиентов, пользователей по инбаундам, `nginx.conf` и хэш. Агенты сообщают возможность `nginx`; агентам без неё панель шлёт JSON Caddy, поэтому панель и ноды обновляются в любом порядке ([MIGRATION_NGINX.md](MIGRATION_NGINX.md)).
2. **Доставка на ноду.** Если поменялись только пользователи, нода получает **дельту** и меняет их через API Xray без перезапуска. Если поменялась структура, нода получает **снапшот** и перезапускает Xray. Новый `nginx.conf` нода проверяет `nginx -t` и применяет по SIGHUP; отвергнутый не применяется, ошибка уходит в панель. Каждое сообщение нода подтверждает.
3. **Статистика.** Каждые 10 секунд нода складывает статистику в очередь с номером `(epoch, seq)` и досылает её, пока панель не подтвердит. Повторная доставка не учитывается дважды.
4. **Изменения из другого процесса.** Если `vynel admin` меняет данные, пока панель работает, панель замечает это, опрашивая `events_outbox` раз в секунду.

## Тесты

| Пакет | Что проверяет |
|-------|---------------|
| `xrayconf` | Рендер шаблонов совпадает с рабочими конфигами (`testdata/`: профиль из Remnawave, инбаунд из гайда VK CDN), наследование, lint |
| `xray` | Настоящий Xray: Reality, добавление и удаление пользователя на лету, статистика |
| `panel/service` | Статусы, продление, доступ групп, токены нод, статистика, сбросы, раскладка nginx: Reality отдельно, SNI-роутер, CDN-источник, старым агентам — Caddy, `nginx -t` для шаблонов |
| `nginxconf` | Сборка конфига; с nginx — настоящий nginx отдаёт сайты, разводит по SNI, обрывает неизвестные имена |
| `certs` | Временный сертификат, локальный CA, перенос из Caddy; с `PEBBLE_BIN` — выпуск по ACME HTTP-01 |
| `node/nginx`, `node/agent` | Запуск и перезагрузка nginx, перенос сертификатов Caddy, переход Caddy ↔ nginx (если nginx не стартовал, возвращается Caddy) |
| `panel/subscription` | Форматы, HWID, заглушки, бан перебора. Xray принимает сгенерированные клиентские конфиги |
| `panel/webapi` | Вход, CSRF-заголовок, секретный путь, API, скрытие секретов, разлогин при смене пароля |
| `e2e` | Две ноды (gRPC и in-process), горячие изменения, работа без панели, отзыв сертификата, лимит трафика. All-in-one на одном IP и домене, Hysteria2 рядом с Reality — с настоящим веб-сервером |

Переменные окружения тестов:

| Переменная | Что | Без неё |
|------------|-----|---------|
| `XRAY_BIN` (+ `XRAY_LOCATION_ASSET`) | Xray | тесты на Xray пропускаются |
| `NGINX_BIN` | nginx с модулем stream, по умолчанию `/usr/sbin/nginx` | тесты на nginx пропускаются, если его нет |
| `PEBBLE_BIN` | Pebble, тестовый ACME-сервер (`make pebble`) | тест выпуска по ACME пропускается |
| `CADDY_BIN` | Caddy (`make caddy`) для пути старых агентов | тесты с Caddy пропускаются |
| `MIHOMO_BIN` | Mihomo | проверки клиентом Mihomo пропускаются |

`make test-integration` собирает Xray, Caddy и Pebble и выставляет их переменные; nginx берётся системный. CI ставит `nginx` и `libnginx-mod-stream` из пакетов и Pebble.

## Как добавить шаблон профиля

1. Создай `internal/xrayconf/templates/<id>.yaml` по образцу двух существующих. Поля описаны в [PROFILES.md §1](PROFILES.md):
   - `variables` — scope, source, generator;
   - `xray_inbound` — JSON с `${VAR}`;
   - `host` — точка подключения;
   - `nginx` — роль `selfsteal`, `reverse_proxy_xhttp` или `certificate`, при необходимости `server_names`, `location: |`, `server: |`;
   - `lint`.
2. Если клиенту нужен новый вид транспорта, добавь его в `service.HostFor` и в форматы `panel/subscription/formats.go`.
3. Добавь golden-тест с эталонным рабочим конфигом в `internal/xrayconf/testdata/`.

## Нагрузочные тесты

Не входят в CI, запускаются тегом `loadtest` (4 ядра, 16 ГБ — цифры ниже с такой машины):

```bash
LOAD_USERS=10000,50000,100000 go test -tags loadtest -run TestLoad -v -timeout 60m ./internal/loadtest/
XRAY_BIN=$PWD/.cache/xray/xray XRAY_LOCATION_ASSET=$PWD/.cache/xray \
  LOAD_USERS=50000 LOAD_ONLINE=5000 go test -tags loadtest -run TestNodeLoad -v ./internal/node/agent/
```

Панель (3 ноды × Reality + Hysteria2, все пользователи в одной группе):

| | 50 000 | 100 000 | 200 000 |
|---|---|---|---|
| Пересчёт состояния всех нод (после каждого изменения) | 0,37 с | 0,68 с | 1,4 с |
| Подписка, 32 клиента одновременно | ~2 900 запр/с, p99 35 мс | ~2 850 запр/с | ~2 800 запр/с |
| Пакет статистики ноды (все пользователи активны) | 0,71 с | 1,35 с | 2,7 с |
| Лимит IP: половина онлайн на 3 нодах, один круг | 0,18 с | 0,38 с | 0,92 с |
| Список пользователей в панели, страница из 200 | | | 7 мс |

Нода (настоящий Xray, 50 000 пользователей): запуск 1,6 с (RSS 73 МБ); 5 000 новых пользователей через API — 2,5 с; при 5 000 онлайн (RSS ~460 МБ) список адресов читается за 0,2–0,3 с; 500 блокировок адресов применяются за 0,14 с.

Где упиралось и что исправлено:
- **Подписки** — ~260 запр/с при любом числе пользователей: на каждый запрос десятки SQL-запросов (настройки, ноды, профили, рендер инбаундов, ключ Reality) через одно соединение SQLite. Теперь конфигурация держится в памяти (`service/cache.go`, сбрасывается при любом изменении через сервис и не позже чем через 10 с при изменениях из другого процесса), а повторные запросы того же приложения ничего не пишут.
- **Новые устройства** писали событие, по которому панель пересчитывала все ноды. Теперь такие события пересчёт не вызывают.
- **Статистика** — 5,2 с на пакет 50 000 пользователей (каждый SQL разбирался заново). Теперь подготовленные запросы и одна проверка лимитов трафика.
- **Список пользователей** — все разом и группы каждого отдельным запросом, каждые 20 с. Теперь страницами.
- **Пересчёт нод** читал всех пользователей целиком ради каскадов, даже без каскадов.
- **Онлайн-адреса** на ноде читались по одному вызову на пользователя дважды (лимит IP и статистика), второй раз под мьютексом агента. Теперь один параллельный опрос.
- **Блокировки адресов**: правило на пользователя — Xray строит матчер адресов для каждого правила (~15 мс): 500 блокировок не успевали за 20 с. Теперь одно общее правило (и точное — для пользователя, который сейчас онлайн с чужого заблокированного адреса), `ss -K` — одним вызовом на сотню адресов.
- **Нода без секции `routing`** в базовом конфиге: Xray ставил заглушку маршрутизатора, и блокировки не применялись вовсе. Теперь секция есть всегда.

- **Нода без секции `routing`** и **пересчёт нод из-за новых устройств** закреплены регрессионными тестами (`TestIPBlocksWithoutBaseRouting`, `TestBuildConfigAlwaysHasRouting`, `TestLastEventIDSkipsDeviceEvents`).

### Память

## Сборки и релизы

Идея: коммитить можно когда угодно, собирается каждый коммит, свой сервер можно обновить на любую сборку и проверить, а всем остальным обновление прилетает только тогда, когда вы сами выпустили релиз.

| | Сборка коммита (канал **dev**) | Релиз (канал **stable**) |
|---|---|---|
| Что это | pre-release `edge-<ветка>` и артефакт запуска CI | обычный релиз `v1.2.3` на вкладке Releases |
| Когда появляется | при каждом push в любую ветку, кроме веток Dependabot (если изменился код), или вручную | когда вы запускаете workflow `release` или пушите тег `v*` |
| Откуда | `.github/workflows/edge.yml` | `.github/workflows/release.yml`, только коммиты из `main`, только если `ci` на нём зелёный |
| Кто получает | только сервер, переведённый на dev (ваш тестовый), и ноды этой панели | все новые установки и все серверы на stable (по умолчанию) |
| Отмечен как | pre-release, не «Latest» | «Latest» (версия с суффиксом, например `1.2.0-rc1`, тоже pre-release и «Latest» не становится) |

Установщик берётся **только из релиза** и ставит бинарь того же релиза (`install.sh` лежит в релизе и записан в его контрольные суммы). Ветка репозитория нигде не используется как источник установки.

### Как это идёт на практике

1. Коммит в ветку (`main`, `test`, `fix-ci`, …). Запускаются `edge` (сборка) и, для PR и `main`, `ci` (тесты, линтер).
2. `edge` публикует pre-release `edge-<ветка>` и прикладывает сборку к запуску. Никто не получает обновление: серверы на stable смотрят на «Latest».
3. Проверка на своём сервере (любой из способов ниже).
4. Когда готово, выпуск релиза. Только теперь серверы на stable видят новую версию (панель показывает «доступно обновление», `vynel update` её ставит).

### Проверить коммит на своём сервере

Без подготовки, ничего публиковать не нужно:

- **Переключить сервер на dev** (панель и данные сохраняются):

  ```bash
  vynel update --channel dev --ref main        # сервер теперь следует за сборками main
  vynel update --check                         # что сейчас работает и что последнее в канале
  ```

  Дальше каждый новый push в эту ветку виден на сервере как обновление (в панели и в `vynel update`). Вернуться к релизам: `vynel update --channel stable`. Если в ветке были миграции базы, возвращайтесь только на релиз, в который они уже вошли: старая версия не откроет базу новой схемы.
- **Панель и её ноды на тестовой ветке.** Ноды обновляются на тот релиз, за которым следует панель: «Обновить всё» или «Обновить» у ноды переводит её на канал панели и ставит ту же сборку. Так все остальные серверы остаются на релизе, а ваша панель с нодами живёт на ветке:

  ```bash
  git switch -c test && git push -u origin test   # edge собирает релиз edge-test, версия v0.1.1-dev.<хеш>
  vynel update --channel dev --ref test           # на панели
  # дальше в панели: «Обновить всё» — ноды встанут на ту же сборку
  ```

  Обратно: `vynel update --channel stable` на панели и снова «Обновить всё».
- **Новая установка той же сборки:** установщик из pre-release ветки сам следует её сборкам:

  ```bash
  bash <(curl -fsSL https://github.com/vyto4ka/vynel/releases/download/edge-main/install.sh)
  # или установщик из релиза с флагами: install.sh --channel dev --ref claude/my-branch
  ```

  В имени релиза `/` ветки заменяется на `-` (`claude/x` → `edge-claude-x`).
- **Точный коммит из артефакта CI:** на странице запуска `edge` (Actions) лежит артефакт `vynel-edge-<ветка>-<версия>` (14 дней). Скачать (`gh run download`), положить `vynel-linux-amd64` на сервер и:

  ```bash
  bash install.sh --mode update --binary ./vynel-linux-amd64
  ```

  Следующий `vynel update` вернёт сервер на его канал, так что тестовая сборка заменится.
- **Сборка без нового коммита:** Actions → `edge` → Run workflow на нужной ветке.

Сборки удалённых веток чистятся автоматически при следующем запуске `edge`, поэтому вкладка Releases не засоряется.

### Выпустить релиз

1. Убедитесь, что нужный коммит уже в `main` и `ci` на нём зелёный (желательно, что вы проверили его на своём сервере, как выше).
2. В `CHANGELOG.md` в `main` есть раздел `## v1.2.0 — дата`: он целиком становится описанием релиза, ниже workflow добавляет команды установки и обновления и список изменений от GitHub. Без раздела стабильный релиз не выпускается, pre-release (`1.2.0-rc1`) выходит и без него.
3. Actions → **release** → Run workflow: `version` = `1.2.0` (тег станет `v1.2.0`), `ref` пустой (конец `main`) или конкретный коммит, который вы проверяли. Либо тегом: `git tag v1.2.0 origin/main && git push origin v1.2.0`.
4. Workflow проверяет версию, что в `CHANGELOG.md` есть раздел, что коммит в `main`, что `ci` на нём прошёл и что такого релиза ещё нет; собирает веб-интерфейс и бинари с версией `v1.2.0`, делает черновик релиза со всеми файлами и публикует его одним действием, чтобы серверы не увидели `VERSION` раньше бинарей. Опубликованный релиз не перезаписывается: ошибку исправляет новая версия.

Первый релиз нужно выпустить до того, как кто-то будет ставить stable: пока `Latest` нет, `releases/latest/download/…` отвечает 404.

### Что делают серверы

- Новая установка по умолчанию на stable (`/etc/vynel/install.env`: `VYNEL_RELEASE=latest`). `vynel update --check` показывает канал, релиз и последнюю версию.
- Серверы, установленные до каналов, остались на `edge-main` (dev). Панель переводится командой `vynel update --channel stable`, её ноды переходят на канал панели при следующем обновлении из панели (агентам до этой версии нужно одно обновление, чтобы понять команду; до тех пор их можно перевести той же командой на самой ноде).
- `VERSION` у dev-сборки — следующий патч после последнего релиза и короткий хеш последнего коммита, который менял код: `v0.1.1-dev.3f2a1bc` (`scripts/code-version.sh --dev`; после `v0.2.0-rc1` это `v0.2.0-dev.…`). У релиза это тег. Панели предлагают обновление, когда версия отличается: правка README его не вызывает, а смена канала да. Список «не кода» в `code-version.sh` и `paths-ignore` в `edge.yml` держи одинаковым.
- Команду установки ноды (`install.command`) установщик записывает в настройки панели; она указывает на `install.sh` релиза, за которым следует панель.

### Файлы

- `scripts/release-assets.sh` готовит каталог релиза (установщик с вписанным `BUILT_RELEASE`/`BUILT_REF`, `SHA256SUMS`, `VERSION`, подпись). Его используют оба workflow.
- `scripts/test-install.sh` проверяет без root и сети, какой релиз выберет установщик в каждой комбинации `--channel`/`--ref`, и что `release-assets.sh` даёт согласованные суммы. Запускается в `ci`.

### Подписанные релизы

- **Что подписывается.** CI (`release-assets.sh`) подписывает `SHA256SUMS` ключом Ed25519 и публикует `SHA256SUMS.signed`: контрольные суммы плюс последняя строка `# ed25519 <подпись>`. Это один файл, поэтому скачивающий никогда не получит суммы и подпись от разных сборок.
- **Что входит.** Бинари `vynel-linux-*` и сам `install.sh`: он тоже лежит в релизе и есть в подписанных суммах.
- **Как проверяется.**
  - Установщик проверяет подпись встроенным открытым ключом (`RELEASE_PUBKEY` в `scripts/install.sh`) обычным `openssl`; дополнительных программ не нужно. Не совпало — бинарь не ставится.
  - `vynel update` (и кнопка обновления в панели) берёт ключ из установщика, встроенного в работающий бинарь, скачивает из релиза `SHA256SUMS.signed` и `install.sh` и запускает установщик, только если сошлись подпись и его сумма (`internal/update/verify.go`). Подпись не сошлась или её нет — обновление останавливается, неподписанного запасного пути нет. В релизе без `install.sh` (старый) берётся установщик из бинаря. Зеркало `--gh-proxy` при этом ничего подменить не может.
  - Xray установщик сверяет с его собственным `.dgst` (SHA2-256), который берёт прямо с GitHub, а через зеркало — только если GitHub не отвечает.
- **Происхождение сборки.** Кроме подписи, релиз получает аттестацию GitHub (`actions/attest`): запись, что бинари и `install.sh` собраны workflow `release` из конкретного коммита. Проверить скачанный файл: `gh attestation verify vynel-linux-amd64 --repo vyto4ka/vynel`. Установщик и `vynel update` на неё не смотрят, им хватает подписи; это проверка для тех, кто хочет убедиться сам.
- **Как включить** (один раз, владелец репозитория):
  1. `scripts/release-key.sh` — создаёт ключ, вписывает открытую часть в `scripts/install.sh` и печатает закрытую.
  2. Закрытый ключ — в секрет репозитория `RELEASE_SIGNING_KEY` (Settings → Secrets and variables → Actions).
  3. Закоммитить `scripts/install.sh`.

  CI сам проверяет, что секрет и ключ в установщике — пара. Если они не совпадают, публикация падает, а не ломает установки. Пока секрета нет, релизы не подписываются, установщик проверяет только суммы, а `vynel update` пишет в лог, что установщик не проверен (он всё равно берётся из релиза, а не из ветки).

  Порядок важен: сначала секрет, потом коммит с ключом. Серверы, обновлённые до сборки с ключом, дальше принимают только подписанные релизы.

## Веб-интерфейс

- Стек: React 19 + TypeScript + Vite, без UI-библиотек; редактор кода — CodeMirror 6 (`web/src/code.tsx`, отдельный чанк). Тема — CSS-переменные в `web/src/styles.css`: компоненты по Material 3 (роли `--primary`, `--secondary-container`, `--container*`, шкала скруглений `--shape-*`, `--elev-*`), нейтральные слои по схеме Catppuccin Mocha в бирюзовом оттенке, акценты — мику-бирюзовый (`--primary`) и розовый (`--tertiary`). Старые имена (`--miku`, `--pink`, `--surface*`) оставлены как псевдонимы.
- Маршруты — через `#/раздел`, поэтому интерфейс работает под любым секретным путём. Запросы — относительные `api/…` с заголовком `X-Vynel: 1` (защита от CSRF).
- API: `internal/panel/webapi/api.go`, список маршрутов — в `routes()`. Новая страница — файл в `web/src/pages/` и строка в `sections` в `web/src/main.tsx`.
- Разработка с горячей перезагрузкой: запустить панель (см. ниже), затем

  ```bash
  cd web && VYNEL_PANEL=http://127.0.0.1:2097/<секретный путь>/ pnpm dev    # http://localhost:5173/
  ```

  Секретный путь и пароль: `bin/vynel admin --data-dir /tmp/vynel web password`.

## Ручной запуск без установки

```bash
sudo apt install nginx libnginx-mod-stream && sudo systemctl disable --now nginx   # свой экземпляр, порты 80/443 нужны vynel
make web build xray
X=.cache/xray
sudo bin/vynel panel --data-dir /tmp/vynel --gateway-listen 127.0.0.1:9443 --public-addr 127.0.0.1:9443 \
  --with-node --xray-bin $X/xray --xray-assets $X --nginx-bin /usr/sbin/nginx --tune-sysctl=false
# во втором терминале
A="sudo bin/vynel admin --data-dir /tmp/vynel"
$A setup --domain nl.example.com --name Нидерланды --country nl
$A setting caddy.issuer internal          # без настоящего домена: сертификаты от локального CA (ключ назван по-старому)
$A setting caddy.http_port 8080           # если порт 80 занят
$A user add vasya && $A user show vasya
$A web password                            # логин и пароль веб-панели; без домена: http://127.0.0.1:2097/<путь>/
$A node list
```
