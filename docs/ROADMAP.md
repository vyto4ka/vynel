## Принципы порядка

1. **Сначала самое рискованное.** Управление Xray (рендер конфига, горячее добавление пользователей, статистика) и связь панели с нодой — фундамент. Если тут что-то не так, переделывать придётся всё остальное.
2. **Вертикальные срезы.** Как можно раньше получить сквозной путь «создал пользователя → нода применила → клиент подключился → трафик посчитался». UI, установщик и бот подключаются к уже работающему ядру.
3. **Своя же схема на каждом шаге (dogfooding).** С вехи α система крутится на реальном сервере на шаблоне A. Каждый следующий этап проверяется вживую.
4. **Заложить сразу то, что дорого менять потом:**
   - привязка всех листенеров к конкретному `IP:порт`;
   - base path у UI и API (секретный путь);
   - `sendThrough` и мульти-IP в рендерере;
   - сервисный слой и outbox событий.

   Сама функциональность скрытия придёт позже, но структуру под неё не придётся ломать.
5. **Тесты на эталонах.** Отрендеренные конфиги профилей A и B сравниваются с рабочими конфигами из PDF и HTML-гайда (golden-файлы). Так совместимость со схемами, которые уже работают, проверяется автоматически.

## Этапы

### Этап 0. Скелет репозитория

- Структура каталогов (ARCHITECTURE §4), `go.mod`, единый бинарь с подкомандами-заглушками.
- Конфиг и логирование (`slog`), `Makefile`: `build`, `test`, `lint`, `proto`, `web`.
- CI: `golangci-lint`, `go test`, сборка `amd64/arm64`. Пустой `web/` с Vite, который собирается и вшивается.
- Dev-окружение: `deploy/dev/docker-compose.yml` — панель и две ноды в контейнерах, плюс контейнер-клиент с Xray для e2e.

**Готово, когда:** `make build` даёт бинарь `vynel`, CI зелёный, `docker compose up` поднимает пустые процессы.

### Этап 1. Ядро Xray (`internal/xrayconf`, `internal/node/xray`)

- Шаблоны A и B в YAML (PROFILES §1.3), загрузка и валидация.
- Переменные: scope, source, генераторы (x25519, shortid, path, port).
- Рендер инбаунда: шаблон ⊕ профиль ⊕ переменные ноды ⊕ override (INBOUNDS §1.4).
- Сборка полного конфига:
  - базовый конфиг;
  - системные секции (`api`, `stats`, `policy`, API-инбаунд);
  - `clients`;
  - `listen`, outbounds `DIRECT@ip` и правила по `inboundTag`.
- Lint (PROFILES §4.8) и `xray run -test`.
- Менеджер процесса Xray: старт, graceful-рестарт, сбор stderr.
- Клиент API Xray: `AddUser`, `RemoveUser`, `QueryStats(reset)`, онлайн-IP.

**Готово, когда:**
- golden-тесты: рендер A совпадает с конфигом из PDF, рендер B — с конфигом из гайда (с точностью до наших системных секций);
- интеграционный тест в CI на настоящем Xray: поднять конфиг → добавить пользователя на лету → подключиться Xray-клиентом → `curl` через прокси → в `QueryStats` есть байты → удалить пользователя → подключение отклоняется.

### Этап 2. Хранилище и сервисный слой (`internal/panel/store`, `service`, `events`)

- Миграции по итоговой модели: ARCHITECTURE §5 + INBOUNDS §3 + STEALTH §4 + INSTALL §4.3.
- Репозитории (`sqlc`), транзакции.
- Сервисы:
  - `Nodes`, `Addresses`, `Profiles`, `NodeInbounds` (с наследованием);
  - `Groups` (`group_access` и развёртка в набор инбаундов);
  - `UserTemplates`, `Users` (статусы, продление `max(now, expire_at)`);
  - `Settings`.
- `events_outbox` и `audit_log` пишутся в той же транзакции, что и изменение.
- Временный CLI `vynel admin user add/list/extend` поверх сервисов — чтобы пользоваться до появления UI.

**Готово, когда:** unit-тесты сервисов (автомат статусов, развёртка доступа групп, наследование override) зелёные, CLI создаёт пользователя по шаблону, указав только имя.

### Этап 3. Связь панели и ноды (`internal/proto`, `gateway`, `reconciler`, `internal/node/agent`)

- `.proto` (ARCHITECTURE §14), внутренний CA.
- `Join` по install-токену: CSR → сертификат.
- Стрим `Connect` с mTLS и обязательным SNI.
- Reconciler:
  - desired state ноды → ревизия;
  - дебаунс;
  - `Snapshot` при подключении или расхождении ревизий;
  - `Delta` (`Upsert/RemoveUser`) в обычном режиме.
- Агент:
  - применение снапшота и дельт к Xray;
  - локальное состояние в bbolt;
  - reconnect с backoff;
  - отчёт об адресах интерфейсов.
- In-memory транспорт для локальной ноды (`--with-node`).

**Готово, когда:** в dev-compose: создать пользователя CLI → через секунду он есть в Xray на обеих нодах без рестарта; убить панель → ноды продолжают работать; поднять панель → ревизии сходятся.

### Этап 4. Статистика и плановые задачи

- Агент собирает `StatsBatch{seq}` в очередь bbolt и отправляет до `Ack`.
- Панель: идемпотентный приём, счётчики, почасовые и дневные агрегаты, метрики нод, онлайн.
- Лимиты: `limited` → удаление с нод.
- Scheduler: истечения, сбросы по `reset_strategy`, свёртка агрегатов, очистка.

**Готово, когда:** e2e — клиент качает файл, `traffic_used` растёт; при превышении лимита клиента отключает; пока панель лежит, трафик копится на ноде и после её подъёма доезжает без дублей.

### Этап 5. Подписки (`internal/panel/subscription`)

- Точки подключения создаются сами для каждого инбаунда ноды, override и `hidden`.
- Листенер подписок: настраиваемый префикс, ответ-заглушка на неверный токен, бан перебора.
- Правила ответа по UA, `client_type`, формат в URL.
- Форматы по порядку: base64 `vless://` → Mihomo → sing-box → Xray JSON (XHTTP `extra` и `xmux` во всех).
- Заголовки `subscription-userinfo` и прочие.
- HWID: реестр устройств, лимит, отказ без `x-hwid` и галочка, которая это разрешает, подписка-заглушка с причиной.
- HTML-страница подписки (простая).

**Готово, когда:** golden-тесты форматов; Happ и v2RayTun на телефоне импортируют подписку и подключаются к ноде из dev-окружения; лимит HWID срабатывает на третьем устройстве.

### Этап 6. Caddy и сеть (`internal/node/caddy`, резолвер портов)

- Резолвер `(IP, порт) → кто слушает` (INBOUNDS §2.3) и превью раскладки с конфликтами.
- Генератор JSON Caddy:
  - сайты с `bind` на IP;
  - строгий SNI;
  - self-steal на `127.0.0.1:8443`;
  - reverse proxy для XHTTP;
  - ACME HTTP-01 без TLS-ALPN;
  - сайты-заглушки.
- Листенеры панели (UI/API, подписки, gRPC) на конкретных адресах.
- Системная подготовка ноды: sysctl (BBR, fq, TFO), лимит файлов, проверка времени.

**Готово, когда:** резолвер покрыт табличными тестами (1, 2, 3 IP; панель и подписки на одном IP; A+B на одном IP); на реальном сервере шаблон A работает как в PDF: браузер видит сайт с валидным сертификатом, клиент подключается.

> **Веха α — «работает у меня».** Один реальный сервер, панель + нода, шаблон A, пользователи через CLI, подписка в Happ, статистика. Ставится вручную через systemd-юниты из `deploy/`.

### Этап 7. Веб-интерфейс

Порядок страниц:
1. Каркас: base path из настроек, временный вход через `vynel admin login-link` (механизм ссылок из STEALTH §3.2B, без бота).
2. Пользователи: список, фильтры, создание по имени, карточка, продление, устройства.
3. Группы и шаблоны пользователей.
4. Ноды: статус, метрики, адреса, инбаунды с пометками «из профиля / изменено на ноде».
5. Профили: форма шаблона + Monaco (JSON-режим), превью «затронет N нод».
6. Точки подключения: ссылка, QR, предпросмотр в клиентах.
7. Мастер «Добавить сервер» (пока только командой), страница-инструкция ноды с живым чеклистом.
8. Дашборд и графики.
9. Настройки: домены, IP и роли, скрытие, HWID, правила ответа.

API для фронта — тонкий транспорт `webapi` над сервисами. Фронт можно начинать параллельно с этапом 3, как только зафиксированы контракты сервисов этапа 2.

**Готово, когда:** всё из CLI доступно в UI, мастер добавления ноды проходит до конца на dev-окружении.

### Этап 8. Telegram-бот

1. Привязка админов кодом, `/invite`, молчание для чужих.
2. Вход: одноразовая ссылка (GET-страница + POST, без превью) и Mini App (проверка `initData`). Отключение входа по паролю по умолчанию.
3. Уведомления о входах, `/sessions`.
4. Пользователи: `/new`, `/find`, карточка с кнопками, устройства, тип клиента, QR.
5. Подписка бота на outbox: нода офлайн/онлайн, ошибки применения, ежедневная сводка.

**Готово, когда:** вход в панель только кнопкой из бота работает с телефона (Mini App) и с компьютера (ссылка); пользователь создаётся из бота за два сообщения.

### Этап 9. Установщик и релизы

- `goreleaser`: бинари, `checksums.txt`, minisign-подпись, GitHub Releases.
- `install.sh` (bootstrap) и `vynel install` (TUI) по INSTALL §2:
  - роли;
  - проверка системы;
  - интерфейсы и IP с ролями;
  - домены с проверкой DNS;
  - режим скрытия;
  - сертификаты;
  - привязка бота кодом;
  - пароль бэкапов;
  - профиль ноды;
  - сводка.
- systemd-юниты, `install.yaml`, повторный запуск (обновить / перенастроить / удалить), `vynel update`.
- `vynel net add-ip` с откатом.
- `node.sh`, отдаваемый панелью по install-токену, и отчёт о прогрессе для страницы-инструкции.

**Готово, когда:** чистый VPS → одна команда → вопросы → через ~3 минуты кнопка входа в Telegram; вариант с 2 IP (панель + подписки / VLESS) проверен на реальном сервере.

> **Веха β — «можно уходить с Remnawave».** UI, вход через бота, установка в одну команду, ноды командой по инструкции.

### Этап 10. Бэкап и восстановление

- `VACUUM INTO`, архив tar+zstd, шифрование age, манифест.
- Ночная отправка в бот, локальная ротация, режим `compact`, деление на части больше 50 МБ.
- Восстановление в установщике: из файла или «пришлю боту», сопоставление старых IP с новыми, миграции схемы.
- `vynel node set-panel` для смены адреса панели.

**Готово, когда:** учения — снести сервер панели → новый VPS → восстановление из бэкапа в Telegram → внешние ноды переподключились сами, пользователи не заметили.

### Этап 11. Установка нод по SSH

- `install_jobs` (лог, шаги, возобновление после перезагрузки страницы), SSH-ключ панели.
- Подтверждение ключа хоста, предпроверка, обнаружение IP, опции (`apt upgrade` + reboot, остановить nginx, отключить пароль SSH).
- Запуск `node.sh`, стрим вывода, уведомление в бот, сохранённый доступ по желанию.

**Готово, когда:** новая нода ставится из панели без захода на сервер руками, включая сервер с двумя IP.

### Этап 12. Шаблон B (XHTTP через VK CDN) и A+B

- Шаблон B, общий `extra` для сервера и клиента, клиентский `xmux`.
- Caddy reverse proxy под XHTTP, раскладка A+B на одном IP.
- Внешние шаги VK на странице-инструкции с подставленными значениями.
- Проверки: CNAME, edge `400`, нет `cache: HIT`, периодический мониторинг edge с алертами.
- Скрытие точки B от клиентов без поддержки XHTTP `extra`.

**Готово, когда:** на реальном VK CDN схема работает так же, как по HTML-гайду, только без ручных шагов на сервере; golden-тест совпадает с гайдом.

### Этап 13. Скрытие целиком

- Секретный путь и высокий порт панели, смена через настройки с новой кнопкой входа в бот.
- Заглушки отдельно для доменов панели и подписок, загрузка своего сайта.
- DNS-01 Cloudflare и wildcard (сборка Caddy с плагином), проверка токена.
- Режим «панель только через VPN» и `login-link --direct`.
- Подтверждение опасных действий в Telegram.

**Готово, когда:** внешний аудит со стороны — сканирование IP (`nmap`, TLS без SNI), crt.sh, перебор путей — не находит признаков панели.

### Этап 14. Надёжность и полировка

- Самотест нод через служебного пользователя, проверка «443 доступен снаружи».
- Режим отладки на 15 минут (лог Xray и Caddy в UI), `capture_headers`.
- Обновление агентов из панели, проверки совместимости версий панели и ноды.
- `vynel node doctor`, документация для пользователя.

## Что сознательно откладываем

- Публичный API и вебхуки для биллинга (структура заложена, ARCHITECTURE §12).
- Шаблоны Reality «чужой сайт», Trojan, SS-2022, WARP outbound, другие CDN.
- Stash, редактор шаблонов подписок, теги нод в `group_access`.
- Docker-образ как альтернативный способ установки.

## Первые конкретные шаги

1. Этап 0 целиком — каркас, CI, dev-compose.
2. Этап 1: шаблон A + golden-тест против PDF + интеграционный тест с настоящим Xray.
3. Этап 2 параллельно с концом этапа 1: миграции и сервисы пользователей и групп.
